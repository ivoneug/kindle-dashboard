# Kindle Dashboard для Claude Code

> **Адаптация Codex (2026-10-29).** Текущая реализация по умолчанию использует Codex: локальный app-server, JSONL-историю и command hooks. Подробности: [docs/codex-integration.md](docs/codex-integration.md). Claude доступен через `DASHD_AGENT=claude`. Ниже сохранён исходный дизайн и результаты M0–M3; M4 пока отложен.

Контекст и ресерч для прототипа. Документ написан для Claude Code: прочитай целиком перед началом работы, начинай с этапа M0 и сначала проверяй на устройстве всё, что помечено **[ПРОВЕРИТЬ]**.

> **Объём работ.** Этап 1 (MVP) — только Claude Code. Всё, что касается Xcode, **отложено на этап 2**: автор не уверен, что эта часть вообще понадобится, решение будет принято после того, как Claude-часть поживёт на столе. На этапе 1 Xcode-часть не реализовывать и под неё ничего специально не закладывать. Достаточно, чтобы список экранов и маппинг клавиш на Mac были расширяемыми. Разделы и пункты этапа 2 помечены **[ЭТАП 2]**.

## 1. Цель

Отдельное устройство рядом с монитором, которое:

- показывает состояние сессий Claude Code (работает / ждёт / нужна реакция, последний инструмент, контекст) и лимиты использования;
- позволяет выполнять действия физическими клавишами: одобрить/отклонить запрос разрешения Claude Code, переключить экран, перейти к сессии.

**[ЭТАП 2]** Показывать состояние Xcode (последний билд, ошибки, тесты) и запускать билд/тесты с клавиатуры.

Устройство: **Amazon Kindle Keyboard (Kindle 3)**, уже с джейлбрейком, новая батарея.

Дизайн и источник данных: собственный проект автора **`claude-thing`** (https://github.com/ivoneug/claude-thing), HUD для Claude Code на Spotify Car Thing. Дизайн переносим в ч/б (раздел 7.1), демон переиспользуем (раздел 4.1).

## 2. Почему Kindle, а не что-то ещё (кратко)

Рассмотренные альтернативы:

| Вариант | Итог |
|---|---|
| Elgato Stream Deck + XL + плагин `agentsd` | Хорош для действий (approve/deny с кнопок уже реализован), но это кнопки, а не экран: статы не показать |
| Corsair Xeneon Edge (14.5" тач) | На macOS работает только как обычный монитор: iCUE и виджеты не поддерживаются, тач требует стороннего драйвера (по словам автора драйвера, панель отдаёт только одиночное касание) |
| ESP32-S3 сенсорные панели (Waveshare 7") | Дёшево, но UI на LVGL/C, долго писать |
| iPad mini + своё SwiftUI-приложение | Сильный вариант, но нужно покупать/выделять устройство |
| **Kindle Keyboard 3** | Уже есть, e-ink всегда включён и не выгорает, **физическая клавиатура = кнопки действий**. Минус: нет тача и цвета, медленное обновление экрана |

Решение: Kindle K3 как «тонкий клиент», вся логика и рендер на Mac.

### Важное ограничение: Go, скорее всего, не подойдёт

Ядро 2.6.26 старее, чем требуют современные версии Go: минимальная версия ядра Linux для Go поднята до 2.6.32 ещё в 2021 году, а с Go 1.24 требуется 3.2. Проект kindleland запускал Go на K3 около 2019 года, но это была старая версия Go. Не трать время на Go, пока shell-клиент не упрётся в потолок.

**Порядок выбора стека на Kindle:**

1. **Shell + busybox + штатные утилиты** (`wget`, `eips`, `waitforkey`). Для MVP этого должно хватить. Нулевой риск по тулчейну.
2. **C**, если понадобится нормальное чтение `/dev/input` или прямой вывод в фреймбуфер. Тулчейн: `koxtoolchain`, таргет `kindle` (покрывает Kindle 2, DX, DXg, 3): `./gen-tc.sh kindle`. Флаги для K3: `-mcpu=arm1136jf-s -mfpu=vfp -mfloat-abi=softfp`.
3. Go: только как эксперимент со старой версией Go, без гарантий.

## 4. Архитектура

```
┌──────────────────────── Mac ─────────────────────────┐         ┌──── Kindle K3 ────┐
│                                                      │  USB-   │                   │
│  Claude Code ──hooks──▶ ┌───────────────────────┐    │  сеть   │  client.sh        │
│                         │  dashd                │    │ (или    │  ├ long-poll      │
│  Xcode ─────────────▶   │  ├ state store        │◀──HTTP────▶ │  │  /version       │
│  (xcodebuild /          │  ├ renderer           │    │  Wi-Fi) │  ├ GET /frame.png  │
│   mcpbridge /           │  ├ HTTP API           │    │         │  ├ eips -g         │
│   Behaviors)            │  └ action executor    │    │         │  └ keys.sh         │
│                         └───────────────────────┘    │         │     waitforkey →  │
│                                                      │         │     GET /key       │
└──────────────────────────────────────────────────────┘         └───────────────────┘
```

Это автономный вариант. Вариант с переиспользованием демона `claude-thing` (рекомендуемый) описан в 4.1: там хуки и state store берёт на себя готовый демон. Xcode-часть схемы относится к этапу 2.

Принципы:

- **Kindle тупой.** Он только скачивает готовую картинку, выводит её и отправляет сырые нажатия клавиш. Вся логика, раскладка клавиш и вёрстка живут на Mac. Любые изменения UI не требуют лезть на устройство.
- **Рендер на сервере.** Это стандартный подход для Kindle-дашбордов: автор Life-Dashboard во второй версии перенёс генерацию картинки на сервер, потому что `eips` требует изображения в специфическом формате.
- **Обновление экрана по событиям**, а не по таймеру.

### 4.1. Переиспользование `claude-thing` (рекомендуемый путь)

У автора уже есть рабочий проект с тем же назначением: **https://github.com/ivoneug/claude-thing** (форк `rithkott/claude-thing`, HUD для Claude Code на Spotify Car Thing). Это одновременно **дизайн-референс** (раздел 7.1) и **готовый источник данных**.

Его Mac-демон (`daemon/`, Node, `127.0.0.1:8790`) уже делает всё, что в разделе 5.1 описано как «сделать с нуля»:

- обнаружение сессий (хуки Claude Code, `claude agents --json`, транскрипты, `/usage`);
- permission bridge: держит хук `PermissionRequest` открытым до ответа, никогда не отклоняет автоматически, по таймауту отдаёт вопрос в терминал;
- очередь всего, что ждёт человека; лимиты использования; поднятие окна терминала нужной сессии;
- WebSocket-хаб `ws://127.0.0.1:8790/ws`. Контракт в `protocol/claude-protocol.md` (в репо он назван единственным источником правды, но местами отстаёт от кода, см. ниже; при расхождении сверяться с `daemon/src/`).

Ключевое из протокола:

- Первый кадр клиента: `bridge.hello` с `{role}`. Роль это произвольная строка (`daemon/src/hub.js`), так что `role: "kindle"` подойдёт. Ответы идут только запросившему сокету, события рассылаются всем.
- Запросы: `claude.sessions.list`, `claude.session.get`, `claude.queue.list`, `claude.permission.answer {requestId, decision: "allow"|"deny"}`, `claude.question.answer`, `claude.session.focus`, `claude.usage.get`.
- События: `claude.sessions.update` (полный снапшот, дебаунс 500 мс), `claude.session.update`, `claude.permission.request {requestId, sessionId, tool, summary, intent, createdTs, timeoutMs}`, `claude.permission.resolved`, `claude.question.request/resolved`, `claude.usage.update` (раз в минуту).
- `SessionSummary`: `name`, `state: busy|attention|celebrate|idle`, `context` (0..1 или `null`), `permissionMode`, `tokens`, `pendingPermission`, `ended`.
- Таймаут разрешения: в `protocol/claude-protocol.md` указано `timeoutMs = 55000`, но в коде `daemon/src/config.js` стоит `PERMISSION_HOLD_MS = 595_000` (~10 мин, переопределяется через `CLAUDE_THING_HOLD_MS`) при `HOOK_TIMEOUT_S = 600`. Верить коду, а `timeoutMs` брать из самого события.
- `claude.permission.answer` принимает только `allow` / `deny` (`daemon/src/permission-bridge.js`). Отдать запрос в терминал сразу, до таймаута, сейчас нельзя: для клавиши `Back` нужно добавить в демон решение `ask` (внутри уже есть `hookDecision('ask')`, используется на таймауте).

**Что это меняет:** `dashd` превращается из «демона с хуками» в **мост**: WS-клиент демона `claude-thing` (роль `kindle`) + рендер + HTTP API для Kindle (+ Xcode-адаптер на этапе 2). Этапы M2 и M3 сокращаются до подписки на события и вызова `claude.permission.answer`.

**Решение (2026-10-28):** демон не подключается по WS, а переносится в репозиторий. Ядро из `rithkott/claude-thing@920192b` (`daemon/src` без WS-хаба, его HTTP-сервера и Bluetooth-ограничений) лежит в `dashd/src/claude/` и работает в процессе `dashd`. Хуки ставит `dashd` (`npm run install-hooks`, порт 8765, только loopback). Доработки под Kindle: без подключённого Kindle разрешение сразу уходит в терминал, при отключении Kindle удерживаемые запросы возвращаются в терминал, `ask` стал допустимым решением (клавиша `Back`). Подробности в `dashd/src/claude/README.md`. Репозиторий теперь под GPL-3.0.

**Важно:** не ставить второй набор хуков `PermissionRequest` рядом с хуками `claude-thing`. Два permission bridge на одном событии будут конкурировать за ответ. Источник разрешений должен быть один.

Архитектура в этом варианте:

```
Claude Code ─hooks─▶ claude-thing daemon :8790 ─WS─▶ dashd (role "kindle") ─HTTP─▶ Kindle K3
                                                       ├ Xcode adapter (этап 2)
                                                       └ renderer → 800×600/600×800 grayscale PNG
```

Язык `dashd` в этом варианте разумнее выбрать JS/Node: тот же стек, что у демона и `device-app`, и можно переиспользовать разметку экранов (см. 5.3, вариант Б). Swift остаётся вариантом, если рендер делать нативно.

## 5. Mac-сторона: `dashd`

> Если идём по пути 4.1, раздел 5.1 (хуки) не реализуется: данные и ответы на разрешения идут через WS-протокол `claude-thing`. Раздел 5.1 оставлен как справка и как запасной план.

Язык: Node/JS при переиспользовании `claude-thing` (4.1), либо Swift (macOS executable / Swift Package) при автономном варианте. Варианты рендера в 5.3.

### 5.1. Источники событий: Claude Code

- Хуки Claude Code шлют события в `dashd`. Нужные события: `SessionStart`, `UserPromptSubmit`, `PreToolUse`, `PostToolUse`, `PermissionRequest`, `Notification`, `Stop`, `SessionEnd`.
- **[ПРОВЕРИТЬ]** актуальную схему хуков, типы (`command` / `http`), таймауты и формат JSON-решения для `PermissionRequest` в документации: https://docs.claude.com (раздел Claude Code → Hooks). Не придумывай схему по памяти.
- Самый надёжный вариант без зависимости от `http`-типа: command-хук с `curl`, который пробрасывает stdin в `dashd` и печатает ответ сервера в stdout. Набросок (схему сверить с докой):

```json
{
  "hooks": {
    "Stop": [
      { "hooks": [ { "type": "command",
        "command": "curl -s -m 5 -X POST --data-binary @- http://127.0.0.1:8765/hooks/Stop" } ] }
    ],
    "PermissionRequest": [
      { "matcher": "", "hooks": [ { "type": "command",
        "command": "curl -s -X POST --data-binary @- http://127.0.0.1:8765/hooks/PermissionRequest",
        "timeout": 600 } ] }
    ]
  }
}
```

- `PermissionRequest`: `dashd` **держит запрос открытым**, пока пользователь не нажмёт клавишу на Kindle или не истечёт таймаут. Так сделано в `agentsd` (держит до 120 с) и `slopdeck` (отпускает на 540 с при таймауте хука 600 с).
- **Правило фолбэка (обязательно): никогда не отклонять автоматически.** Нет Kindle, таймаут, ошибка, перезапуск `dashd` → вернуть «нет решения», чтобы диалог появился в терминале как обычно. Подход взят из `slopdeck`.
- Очередь запросов разрешений: FIFO, на экране старейший, рядом счётчик ожидающих.
- Контекст и токены: из JSON statusline / JSONL-транскриптов сессии. Лимиты 5h/weekly: необязательно и хрупко (Clawdmeter достаёт их из заголовков ответов API через OAuth-токен), отложить.
- Не путать с официальным **Remote Control** (`claude remote-control`): это одобрение и мониторинг из мобильного приложения Claude. Он может работать параллельно как запасной канал.

### 5.2. [ЭТАП 2] Источники событий и действия: Xcode

> Отложено. На этапе 1 не реализовывать. Раздел сохраняет ресерч, чтобы не искать заново, если этап 2 понадобится.

Варианты по возрастанию сложности:

1. **Xcode Behaviors** (Settings → Behaviors → Build Starts / Succeeds / Fails → Run script) с `curl` в `dashd`. Пассивно ловит билды, запущенные из GUI.
2. **`xcodebuild`** для действий с Kindle (`B` → build, `T` → test) с `-resultBundlePath` и разбором через `xcrun xcresulttool`. Не зависит от открытого Xcode. **Рекомендуется как первый шаг этапа 2.**
3. **`xcrun mcpbridge`** (Xcode 26.3+): официальный MCP-мост, 20 инструментов, включая `BuildProject`, `RunTests`, `XcodeRead`, `RenderPreview`. Требует запущенный Xcode с открытым проектом и включённый MCP в Settings → Intelligence. Известная проблема: повторяющийся системный диалог «Allow access to Xcode?», если процесс моста каждый раз новый (решается долгоживущим мостом, см. `xcode-cli`). Последний шаг этапа 2.

### 5.3. Рендер

- Холст **600×800** (портрет) или **800×600** (ландшафт, перед отдачей повернуть на 90°). **[ПРОВЕРИТЬ]** ориентацию вывода `eips`.
  - Ландшафт 800×600 почти совпадает с 800×480 у Car Thing: раскладку `claude-thing` можно перенести почти один в один, а лишние 120 px отдать под легенду клавиш. Минус: Kindle стоит боком, клавиатура сбоку.
  - Портрет: клавиатура естественно снизу, но раскладку экранов придётся перекомпоновать (тайлы сессий в один столбец).
  - Решить на M1: оба варианта рендера дешёвые, сравнить вживую.
- **Вариант А (Swift):** SwiftUI `View` → `ImageRenderer` → `CGImage` → перерисовать в 8-bit `CGColorSpaceCreateDeviceGray()` **без альфы** → PNG через `CGImageDestination`.
- **Вариант Б (переиспользование разметки, рекомендуется при пути 4.1):** взять рендер экранов из `claude-thing/device-app/src/screens/*.js` (они возвращают HTML-строки из состояния), подключить отдельную e-ink тему (переопределить токены `:root` из `device-app/src/styles.css`, выключить анимации), отрисовать в headless Chrome (Playwright/Puppeteer) в нужном размере, снять скриншот и сконвертировать в 8-bit grayscale без альфы. Экраны рассчитаны на Chrome 69, так что в современном Chrome проблем быть не должно.
- **PNG должен быть grayscale с `color_type` 0**, иначе `eips` его не покажет. Для отладки: `pngcrush -c 0`. Добавить проверку в тест.
- Квантовать в 16 уровней серого. Крупные шрифты, никаких тонких линий и полупрозрачности.
- Статусы различать формой и инверсией (чёрная плашка = нужна реакция), не цветом.
- Дебаунс рендера ~300–500 мс, склеивать пачки событий в один кадр.

### 5.4. HTTP API (shell-friendly, без заголовков)

| Метод | Путь | Назначение |
|---|---|---|
| GET | `/version?since=N` | Long-poll. Держит запрос до появления кадра с версией > N или ~25 с. Отвечает текстом: номер текущей версии. |
| GET | `/frame.png?v=N` | PNG кадра версии N. |
| GET | `/key?code=K&v=N` | Нажатие клавиши. `v` = версия кадра, который сейчас на экране. |
| GET | `/full?v=N` | (опц.) Подсказка клиенту делать полное обновление. Можно вместо этого кодировать в ответе `/version`, например `42 full`. |
| POST | `/hooks/{Event}` | Приём хуков Claude Code. |
| POST | `/xcode/{event}` | **[ЭТАП 2]** Приём событий Xcode Behaviors. |

**Защита от «нажал не на то»:** действие с клавиши применяется только если `v` совпадает с версией кадра, на котором показан этот запрос разрешения. Иначе игнорировать и перерисовать.

### 5.5. Безопасность

- По умолчанию слушать на USB-интерфейсе (`192.168.2.1`) и `127.0.0.1`. Wi-Fi добавляет конкретный приватный IPv4 Mac (`lanHost`), только с общим секретом. Не `0.0.0.0`.
- Wi-Fi: случайный ключ на 256 бит в query-параметре, проверяется на `/version`, `/frame.png` и `/key`; хуки и служебные страницы остаются только на loopback. Локальные настройки и ключи исключены из Git. Настройка и возврат к USB описаны в README.
- `dashd` не выполняет произвольных команд с Kindle: только фиксированный набор действий.

## 6. Kindle-сторона

### 6.1. Подготовка устройства (джейлбрейк уже есть)

1. Установить хак **USBNetwork** (если ещё нет). Включение на K3 из строки поиска: `;debugOn` → `~usbNetwork` → `;debugOff`.
2. Адреса для K3: **Mac 192.168.2.1, Kindle 192.168.2.2**. Исходный вариант из старых гайдов (Mac 192.168.1.1, Kindle 192.168.1.2) отменён: домашняя сеть Mac находится в 192.168.1.0/24 (Wi-Fi 192.168.1.247), и подсети пересекаются. DHCP нет, адрес на Mac назначить вручную на появившийся USB-интерфейс (`en*`, смотреть `ifconfig` до и после подключения). Это заводские значения USBNetwork 0.57.N для K3 (`HOST_IP` / `KINDLE_IP` в `/mnt/us/usbnet/etc/config`); подсеть 192.168.15.x в его README относится к K4.
   - **[ПРОВЕРИТЬ]** что современная macOS видит USB-сеть K3. Инструкции на форумах 2012–2018 годов. Если не заведётся: Wi-Fi + статический IP / DHCP-резервация на роутере.
3. `ssh root@192.168.2.2` (опции для старого dropbear см. в README).
4. Все свои файлы класть в `/mnt/us/dash/`. **Не трогать корневую ФС** без крайней необходимости. Страховка: K3 можно восстановить через USB-downloader режим (Vol+ при включении), но лучше не доводить.

### 6.3. Захват экрана у штатного UI

- Остановить UI: `/etc/init.d/framework stop` (вариант из kindleland), либо заморозить процессы: `killall -STOP cvm` (вариант из скрипта погодного дашборда для K3).
- Не дать уснуть: `killall -STOP powerd`.
- Восстановление: `killall -CONT cvm powerd` или `/etc/init.d/framework start`.
- Тест вывода: `eips -c` (очистка), `eips -g test.png`.
- **[ПРОВЕРИТЬ]** доходят ли нажатия до `waitforkey`, когда UI остановлен, и не реагирует ли на них UI, если он только заморожен.

### 6.4. MVP-клиент (набросок, сверить с результатами discovery)

`/mnt/us/dash/client.sh`:

```sh
#!/bin/sh
BASE="http://192.168.2.1:8765"
V=0
cd /var/tmp
while :; do
  NEW=$(wget -q -O - "$BASE/version?since=$V") || { sleep 2; continue; }
  NEW=${NEW%% *}
  if [ -n "$NEW" ] && [ "$NEW" != "$V" ]; then
    if wget -q -O frame.png "$BASE/frame.png?v=$NEW"; then
      eips -g frame.png            # [ПРОВЕРИТЬ] флаг полного обновления
      V=$NEW
      echo "$V" > /var/tmp/dash.version
    fi
  fi
done
```

`/mnt/us/dash/keys.sh`:

```sh
#!/bin/sh
BASE="http://192.168.2.1:8765"
while :; do
  KEY=$(waitforkey)                # [ПРОВЕРИТЬ] формат вывода
  V=$(cat /var/tmp/dash.version 2>/dev/null)
  wget -q -O /dev/null "$BASE/key?code=$KEY&v=$V"
done
```

`/mnt/us/dash/start.sh`: заморозить `cvm`/`powerd`, запустить оба скрипта в фоне. `stop.sh`: убить их и разморозить UI.

### 6.5. Стратегия обновления e-ink

- Полное обновление со вспышкой ~1 с, частичное оставляет «призраки».
- Частичное обновление для мелких изменений, полное: при смене экрана, при появлении запроса разрешения, и каждые ~10 частичных.
- Никаких анимаций и бегущих логов. Минимальный интервал между кадрами ~1 с (решает дебаунс на сервере).

## 7. Дизайн, экраны и клавиши

### 7.1. Дизайн-референс: `claude-thing`

**https://github.com/ivoneug/claude-thing**. Автору нравится этот дизайн. E-ink версия должна читаться как узнаваемая ч/б адаптация этого дизайна, а не как новый стиль.

Где смотреть:

- `design-handoff/screens/`: исходные макеты `session-list.html`, `session-detail.html`, `permission.html`, `ambient.html`.
- `device-app/src/styles.css`: токены (`:root`) и все стили под 800×480.
- `device-app/src/screens/*.js`: разметка экранов (`session-list`, `session-detail`, `queue`, `ask`, `usage`, `ambient`) и `helpers.js` (топбар, ярлыки состояний и режимов, детектор деструктивных команд).
- `device-app/src/sprites/*.svg`: пиксельный маскот Clawd, полоски по 4 кадра 16×16 (`working`, `attention`, `celebrate`, `sleeping`, `dance-*`, `usage-*`, а также цветовые варианты `mono-*`, `amber-*`, `coral-*`).

Язык дизайна (из CSS и комментариев в коде):

- **Направление «приборная панель»:** тёплые тёмные фоны, лампы-индикаторы состояния, гравированные капсовые подписи с разрядкой (`letter-spacing` 0.16–0.2em).
- **Шрифты:** Chakra Petch 500/700 (основной) и JetBrains Mono (часы, команды, числа). Оба вшиты в CSS как woff2.
- **Читаемость:** на 800×480 с расстояния ~1 м ничего мельче 14 px, всё, что читается мельком, от 19 px.
- **Топбар 46 px:** квадратная метка-акцент, капсовый заголовок экрана, счётчик, часы моноширинным, точка статуса связи.
- **Тайл сессии:** лампа + ярлык состояния (`WORKING` / `ATTENTION` / `DONE` / `IDLE` / `ENDED`), чип режима разрешений (`PLAN` / `AUTO` / `EDITS` / `BYPASS` / `MANUAL`), имя проекта, подстрока (текущий инструмент · последнее сообщение, либо «needs your answer», либо «finished Nm ago»), спек-строка `модель · effort`, полоса контекста с подписью `CONTEXT NN%`, которая инвертируется внутри заливки, маскот в углу.
- **Главное правило:** насыщенный цвет означает «нужен человек». Цветная шапка только у тайла в `ATTENTION`, у остальных структурная.
- **Контекст** нейтральный до 80%, «горячий» от 80%.
- **Очередь:** «герой» (запрос, на который отвечать следующим) занимает экран, остальные стопкой ниже (до 2). У героя hazard-полоса (диагональные полосы), строка `PERMISSION REQUEST` или `PERMISSION REQUEST · DESTRUCTIVE`, время ожидания, имя сессии, intent («you asked: …»), сводка команды, чипы allow/deny.
- **Деструктивные команды** (regex в `helpers.js`: `rm -`, `--force`, `--hard`, `DROP`, `TRUNCATE`, `mkfs`, `dd if=`, `chmod 777`, `curl … | sh`) требуют второго нажатия allow.
- **Usage:** полосы лимитов с порогами: до 80% `ALL CLEAR`, 80–99% `RUNNING OUT`, 100% `OUT OF USAGE`. У каждой полосы свой маскот по «настроению».
- **Пустые состояния:** короткие капсовые фразы (`NOTHING WAITING ON YOU`, `NO SESSIONS — START CLAUDE ON YOUR MAC`).
- **Ambient:** часы и бродящий маскот.

Перевод на e-ink (16 оттенков серого, без цвета, без анимации):

- **Тема.** Переопределить токены. По умолчанию светлый фон (бумага) и тёмный текст; **инверсия (чёрный тайл / плашка) = «нужен человек»**: прямой перевод правила про насыщенный цвет. Тёмная тема тоже возможна, но при частичных обновлениях на тёмном фоне призраки заметнее. **[ПРОВЕРИТЬ]** обе темы на устройстве.
- **Цветовые смыслы → форма.** Лампы различать фигурой и заливкой: busy залитый квадрат, attention инверсный тайл + `!`, done галочка, idle пустой контур. Чипы allow/deny различать текстом и толщиной рамки.
- **Hazard-полоса** переносится в ч/б как есть.
- **Полоса контекста** с инвертирующейся подписью для ч/б идеальна, оставить. «Горячий» контекст: штриховка или жирная рамка.
- **Маскот без анимации:** один статичный кадр на состояние, масштаб целым множителем (16 → 64 px, nearest neighbour). Можно брать следующий кадр полоски при каждом новом кадре экрана. Цвета кадра свести к чёрному.
- **Шрифты** оставить те же. На 6" экран смотрят ближе, чем на Car Thing, так что минимумы 14/19 px можно сохранить и проверить вживую. Линии толщиной 1 px сделать 2 px.
- **Никаких** `blink`, `breathe`, marquee: длинные имена обрезать многоточием.

### 7.2. Экраны (по мотивам `claude-thing`)

1. **Sessions.** Сетка тайлов: в ландшафте 2×2, как в оригинале; в портрете один столбец по 3–4 тайла. Выбранный тайл: жирная рамка.
   - **Детальный экран сессии** (открывается центром джойстика с тайла, как в `claude-thing`): состояние, режим, папка · модель · effort · время работы, текущий инструмент, контекст, токены in/out и cache read. Последнее сообщение показывается целиком, до 4000 символов, и листается страницами.
2. **Queue / Permission** (перекрывает любой экран при новом запросе): герой + стопка, как в оригинале. Вместо нажимаемых чипов подвал с легендой клавиш: `Y` allow · `N` deny · `Back` ответить на Mac. Вопросы (`AskUserQuestion`) и подтверждение плана с Kindle ответить нельзя: ни один хук на них не отвечает, а набирать клавиши можно только в Terminal.app, тогда как сессии автора идут в приложении Claude. Kindle их показывает и по центру джойстика поднимает окно сессии.
3. **Usage.** Полосы лимитов.
4. **Ambient.** Часы, когда всё тихо. Минимум обновлений (раз в минуту).

**[ЭТАП 2]** **Xcode** (новый экран в том же стиле): топбар `XCODE`, тайл последнего билда (схема, `BUILDING` / `SUCCEEDED` / `FAILED`, длительность), первые 3–5 ошибок моноширинным шрифтом, тесты passed/failed; подвал `B` build · `T` test.

## 10. Результаты discovery на устройстве

Снято 2026-10-28, Kindle 3 Wi-Fi (серийник `B008…`).

**Система**
- Прошивка Kindle 3.1 (`031-S1-055870`), ядро `2.6.26-rt-lab126 armv6l`, 256 MB RAM.
- Джейлбрейк NiLuJe 0.7.N (`/mnt/us/linkjail`). USBNetwork 0.57.N установлен из `kindle-usbnetwork-0.57.N-k3.zip`. Пакет пришлось переименовать в нижний регистр (`update_usbnetwork_…`): `linkjail` сверяет имя с белым списком с учётом регистра.
- Часы устройства стоят на 2010 году, RTC не держит время. Для дашборда это неважно: время рисует Mac.

**Связь**
- USB-сеть: Mac `192.168.2.1`, Kindle `192.168.2.2` (заводские значения хака для K3). На macOS Kindle виден как сервис «RNDIS/Ethernet Gadget» (`en10`), адрес назначается вручную, без роутера. VPN с маршрутом по умолчанию не мешает: маршрут до `192.168.2.2` идёт через `en10`.
- Wi-Fi dashboard (проверено 2026-10-29): Mac `192.168.1.247`, Kindle получил `192.168.1.147` по DHCP на `wlan0`. Кадры и клавиши идут через домашний роутер с парным ключом. Пользователь отключил USB и подтвердил переключение `U` / `S` без кабеля. USBNetwork и его SSH-настройки сохранены; доступ SSH по Wi-Fi для dashboard не включался. Настройка описана в README, локальные адреса и ключ исключены из Git.
- SSH: `dropbear_2015.68`, современный OpenSSH подключается без устаревших опций. Root по USB пускается с любым паролем. Вход по ключу `~/.ssh/kindle_k3`, ключ лежит в `/mnt/us/usbnet/etc/authorized_keys`. `HOME` root — `/tmp/root`. `scp -O` работает.
- PATH ssh-сессии `/usr/bin:/bin`, без `/usr/sbin`, поэтому скрипты задают PATH сами.

**Утилиты**
- BusyBox 1.7.2: нет `grep -E`, `timeout`, `nohup`, `setsid`. `wget` умеет только `-c -s -q -O -P -U -Y`, **таймаута нет**: в `config.sh` добавлена обёртка `fetch` со сторожевым таймером. BusyBox 1.23.2 из USBNetwork (`/mnt/us/usbnet/bin/busybox`) почти пустой, `wget` в нём тоже нет.
- `eips` лежит в `/usr/sbin/eips`. Usage: `eips [-c|-n|-i [1]|-f] [-b|-g|-o|-m|-p|-s|-z] [[xpos ypos string|file]|num|[row count [stop]]]`. `-g` выводит PNG с частичным обновлением, `-f -g` с полным. PNG grayscale `color_type 0` из `dashd` показывается, проверено снимком фреймбуфера (`/mnt/us/usbnet/bin/fbgrab`).
- `eips -i`: фреймбуфер `eink_fb` 600×800, 4 bpp, grayscale, `rotate 0`.
- Звук: есть `aplay`, `amixer`, `alsamixer`, `alsactl`.

**Ввод**
- `/proc/bus/input/devices`: `mxckpd` → event0 (клавиатура), `fiveway` → event1 (джойстик), `volume` → event2.
- `waitforkey` печатает одно событие и завершается: `<linux keycode> 1` на нажатие, `<linux keycode> 0` на отпускание (это отдельный вызов). `keys.sh` отпускания отбрасывает. Клавиши доходят до него, когда UI заморожен через `killall -STOP cvm`.
- Между вызовами `waitforkey` устройство ввода закрыто. Событие, пришедшее в этот момент, теряется: при прогоне M1 одно отпускание пропало. Для осознанных нажатий это не мешает. Если начнут теряться нажатия, нужен постоянный читатель `/dev/input/event*` на C (§3).
- Коды: `Y 21`, `N 49`, `S 31`, `Q 16`, `U 22`, `R 19`, `Back 158`, `Home 102`, `Menu 139`, `Del 14`, джойстик ↑ `103` ↓ `108` ← `105` → `106`, центр `194`, левые кнопки перелистывания Next `104` / Prev `193`, правые Next `191` / Prev `109`, `Sym 126`, `Aa 190`, `Shift 42`, `Enter 28`, `Space 57`, громкость + `115` / − `114`. `Alt` до `waitforkey` не доходит.
- Маппинг лежит в `dashd/src/keys.js`, клавиша выхода `KEY_EXIT="102 1"` (Home) — в `kindle/dash/config.sh`.

**Штатный UI** (проверено на прогоне M1): после `killall -CONT cvm` он перерисовывается сам, нажатия, сделанные во время работы дашборда, задним числом не срабатывают. Режим `freeze` подходит, `framework stop` не нужен.

**Заставка и `powerd`** (выяснено на M2): если Kindle успел уйти в заставку, клавиатура выключена, и счётчик прерываний `mxckpd` не растёт. Если при этом заморозить `powerd`, разбудить устройство некому: дашборд рисуется, но не слышит клавиш. Поэтому `start.sh` больше не останавливает `powerd`. Он будит устройство (`lipc-set-prop com.lab126.powerd wakeUp 1`, если `state` не `active`) и включает `preventScreenSaver 1`, а `stop.sh` выключает его обратно. `powerd` продолжает следить за батареей и зарядкой. Его свойства: `lipc-probe -v com.lab126.powerd` (`state`, `preventScreenSaver`, `deferSuspend`, `wakeUp`, `battLevel`, `isCharging` и др.).

**Разрешения с Kindle** (проверено на M3, 2026-10-28): запросы `PermissionRequest` из сессий в десктопном приложении Claude приходят в `dashd`, удерживаются и отвечаются клавишей `Y` на Kindle. В логе: `permission held: date` → `-> allow` через 15 с, по нажатию `Y` на кадре v41.

**Ещё не проверено:** поведение батареи при долгой работе без USB. Подходит ли `wakeUp` для выхода из заставки, тоже не проверено: в прогоне Kindle к этому моменту уже был активен.
